# Pane model: a band-ordered replacement for `$area`

Recorded 2026-09-11. Two goals: (1) a mold that lets graph-viz, obelisk,
and heathcliff describe a pane to urui as data; (2) the plan that lands it
in urui and migrates graph-viz and obelisk onto it.

Follows the naming standard in `remaining-work-plan.md`
(`## Phase <n> — Name`, `### W<phase>.<item> — Title`, `Scope:` tier +
estimate). This document is the live plan for Phases 9–11. Phase 11 was
rewritten 2026-09-25 and absorbs what remained of Phase 8 (obelisk
increment 1); see §3.

---

## 1. What the current mold cannot say

`$area` in `desk/sur/urui.hoon` fixes one layout:

```
pane-header (heading + status + controls)
tab strip           (iff strip=&)
body                (consumer marl)
editor host         (iff secondary=^)
```

Six requirements fall outside it.

| Requirement | Why `$area` cannot express it |
| --- | --- |
| Every pane is tabbed, including the read-only reference pane | the reference area renders the explorer strip through `permanent-views`, a different mechanism from `strip=&` |
| Heading bar *below* the tabs (obelisk's urQL editor) vs *above* them (obelisk's output) | `++workspace-area` and `++section` both hardcode header → strip → body |
| Up to three tab levels (obelisk results) | one strip per area, `{kind}-document-tabs` |
| An optional `+` new-tab control, only on read/write panes | the `+` exists but is switched by a **javascript** hook (`tabHooks(name).add`), not by config |
| Several control rows, some of them disclosure sub-panes (graph-viz node/edge attributes) | one `controls=marl` slot, always visible |
| User hide/reveal of control and header sub-panes, persisted | no concept of a hideable region |

The shared shape behind all six: **a pane is an ordered stack of
horizontal bands, one of which is a tab strip and one of which is the tab
panel.** Ordering the bands is what makes "heading above the tabs" and
"heading below the tabs" the same declaration with two orderings, and it
is what lets a pane carry three control rows instead of one.

## 2. Goal 1 — the proposed mold

Replaces `$area` in `desk/sur/urui.hoon`. `$editor`, `$area-role`,
`$doc-kind`, and everything else in the file are unchanged; `$area-role`
is renamed `$pane-role` with the same three values.

```hoon
+$  pane-role  ?(%reference %editor %result)
::
+$  pane-mode
  ::  %read-only forbids the `+` control, tab close, dirty marks, and
  ::  every file-write path into the pane, whatever a band declares.
  ::
  ::  It does not forbid document tabs: a read-only pane may carry a
  ::  %documents or %views level and show an imported copy of anything
  ::  the editor pane can open.
  ?(%read-only %read-write)
::
+$  reveal
  ::  Whether the user may hide a band, and where that choice persists.
  ::
  ::  `key` is a field of the urui-owned `paneBands` session record; ~
  ::  pins the band open and renders no toggle.  `label` names the
  ::  toggle for assistive technology.
  $:  key=(unit @t)
      open=?
      label=@t
  ==
::
+$  tab-source
  ::  Where one level's tabs come from.
  ::
  ::  %views      the explorer strip: `fixed` seeds it and the runtime
  ::              appends documentation tabs and one reference tab per
  ::              imported document, for every $doc-kind with refs=&
  ::  %documents  the $doc-kind tab store — clay-backed, persisted
  ::  %fixed      exactly `fixed`, for the life of the page
  ::  %dynamic    replaced wholesale by `runtime.panes.set`
  $?  %views  %documents  %fixed  %dynamic  ==
::
+$  tab-level
  ::  One depth of tabs inside a pane, outermost first.
  ::
  ::  The strip's element id is `{pane-id}-{name}-tabs`.  Depth 0 is
  ::  emitted by urui-shell; deeper strips are generated by the runtime,
  ::  once per open parent tab.  `add=~` renders no `+` control.
  $:  name=@tas
      label=@t
      source=tab-source
      kind=(unit @tas)
      fixed=(list [name=@tas label=@t])
      add=(unit @t)
      close=?
      reorder=?
  ==
::
+$  band-item
  ::  %label    one line of text, nothing else
  ::  %heading  title, status span, and right-justified actions
  ::  %controls consumer marl, laid out as one row
  ::  %tabs     the tab strips, outermost level first
  ::  %panel    the tab panel: an optional Ace host plus consumer marl
  $%  [%label text=@t]
      [%heading title=(unit @t) status-id=(unit @t) actions=marl]
      [%controls =marl]
      [%tabs levels=(list tab-level)]
      [%panel id=@t host=(unit editor) body=marl]
  ==
::
+$  band
  ::  One horizontal sub-pane, rendered in the order given.
  ::
  ::  Band order is the whole layout language: a %heading before the
  ::  %tabs band is a heading above the tabs, after it is a heading
  ::  below them.  `name` is the band's id fragment, `{pane-id}-{name}`.
  $:  name=@tas
      =reveal
      item=band-item
  ==
::
+$  pane
  ::  One UI region: a mode and the bands stacked inside it.
  ::
  ::  Exactly one band is %tabs and exactly one is %panel; tab levels
  ::  below depth 0 are nested inside the panel by the runtime, not
  ::  declared as further bands.
  $:  role=pane-role
      id=@t
      label=@t
      mode=pane-mode
      kind=(unit @tas)
      bands=(list band)
  ==
```

`$shell-spec` changes one field:

```hoon
      areas=[reference=area editor=area result=area]     ::  was
      panes=[reference=pane editor=pane result=pane]     ::  is
```

`$app-config` loses `permanent-views`. It moves to the reference pane's
`%views` level, which is now the single source of truth; `urui-config`
derives the emitted `permanentViews` from it, and `++build` chooses the
compact or full frame by whether that level exists. See W9.3.

### 2.1 Every requirement, as a declaration

| Requirement | Declaration |
| --- | --- |
| every pane tabbed | every `$pane` carries a `%tabs` band |
| read-only reference pane | `mode=%read-only`; its level has `add=~`, `close=|` |
| any editor document importable read-only | the kind's `refs=&`; the runtime appends a reference tab to the reference pane's `%views` level |
| ship `@p` sub-pane | `[%label text=(scot %p our)]` band, in the reference pane only — urui puts no ship label in the app header |
| heading below tabs | `%tabs` band listed before the `%heading` band |
| heading above tabs | `%heading` band listed before the `%tabs` band |
| three tab levels | three entries in `levels` |
| optional `+` | `add=`'Add empty DOT tab'`` vs `add=~` |
| several control rows | several `%controls` bands |
| reveal sub-panes | `reveal=[key=`'nodeAttrs' open=| label='Node attributes']` |

### 2.2 The three real panes, expressed

**obelisk editor** — tabs first, then the simple heading bar.  The tabs
are obelisk's own, so the level is `%dynamic`, not `%documents`:

```
[%tabs ~[[%script 'Query tabs' %dynamic ~ ~ `'New query tab' & &]]]
[%heading `'urQL' ~ markdown-toggle-save-copy-actions]
[%panel 'editor-body' `ace-host previews]
```

**obelisk output** — heading bar first, then one command level; each
command's Results/Messages view and its stacked result sets stay
obelisk's own markup inside the panel (decided 2026-09-25):

```
[%heading `'Output' `'output-status' save-copy-actions]
[%tabs ~[[%command 'Command results' %dynamic ~ ~ ~ | |]]]
[%panel 'results' ~ ~]
```

**graph-viz editor** — heading, file controls, tabs, then two revealable
attribute sub-panes below the visual-tools row:

```
[%heading `'DOT source' `'source-status' ~]
[%controls file-actions]
[%tabs ~[[%dot 'Open DOT documents' %documents `%dot ~ `'Add empty DOT tab' & &]]]
[%controls visual-tools]
[%controls node-attributes]     ::  reveal=[`'nodeAttrs' | 'Node attributes']
[%controls edge-attributes]     ::  reveal=[`'edgeAttrs' | 'Edge attributes']
[%panel 'dot' `dot-ace-host ~]
```

**graph-viz reference** — the explorer, read-only, with the ship label:

```
[%tabs ~[[%view 'Graph Viz explorer' %views ~ ~[[%dot-files 'DOT Files']
                                                [%svg-files 'SVG Files']] ~ | &]]]
[%label (scot %p our)]
[%panel 'explorer' ~ ~]
```

The `%views` level carries three classes of tab at once: the two seeded
file trees, documentation tabs, and one read-only reference tab per
imported document — that last is how "anything the editor pane can open
can be imported into the reference pane" is expressed, and it needs no
extra level. A consumer that wants imports on their own strip instead
declares a second, `%documents` level in the same read-only pane.

### 2.3 What stays out

- The frame itself — header, splitters, explorer resizer, help panel,
  dialogs, context menu — stays urui-owned and outside `$pane`.
- No band nests another band. A pane is a flat list; nesting lives only
  in the tab levels, and only the runtime builds it.
- No consumer vocabulary enters the mold: `%dot`, `%urql`, `Command`,
  `~zod` all arrive as `@tas`/`@t` values the consumer supplies.

## 3. Goal 2 — the implementation plan

Dependency: none on Phase 8. The 2026-09-25 rewrite of Phase 11 absorbs
it: W8.1's inventory is folded into W11.3–W11.5, W8.2 is dropped (obelisk

that changes `$shell-spec` breaks a consumer until that consumer's own
commit lands. Every phase boundary below is therefore a **paired commit**:
urui, then `bin/sync.sh` into the consumer, then the consumer's own
change, then re-record digests. Same workflow as W4.3.

#### W9.4 — Runtime reads `panes` (done 2026-09-15)

Files: `desk/lib/urui-js.hoon`.
Change, in four parts:

1. **Band reveal.** New `runtime.panes.reveal(paneId, bandName, open)`,
   a toggle handler bound to every `{pane}-{band}-toggle`, and a new
   urui-owned `%record` session slot `paneBands` holding
   `{"{pane}.{band}": bool}`. No new `$slot` shape — `%record` already
   carries an arbitrary object.
2. **`add` becomes declarative.** `renderTabs` reads the level's `add`
   instead of `tabHooks(name).add`; a `%read-only` pane never renders it.
   The `add` javascript hook is deleted.
3. **Tab levels.** `renderTabs(name)` generalises to
   `renderLevel(paneId, depth, path)`; depth 0 renders into the shell's
   strip, depth *n* renders a generated strip into the active panel of
   depth *n-1*. `%fixed` levels render from config, `%dynamic` levels
   from `runtime.panes.set(paneId, levelName, tabs, parentPath)`,
   `%documents` from the existing store, `%views` from the existing
   explorer machinery. A second urui-owned `%record` slot, `panePaths`,
   persists the selected path per pane.
4. **New dispatch group.** `window.urui.panes` forwarding to the
   consumer, and `runtime.panes` exposing `get`, `set`, `select`,
   `panel(paneId, path)`, and `reveal`.

Verify: new `test-pane-contract` arm; all 10 node scenarios; new node
coverage for a 3-level strip, a reveal round-trip through the session,
and read-only refusal of `+`/close.
Done: `tabHooks(...).add` no longer exists; `renderTabs` no longer
assumes one strip.

#### W10.5 — Settings modal and screen format (done 2026-09-25)

Files: `desk/lib/urui-shell.hoon`, `desk/lib/urui-css.hoon`,
`desk/lib/urui-js.hoon`, `tests/fixture/lib/urui-fixture-web.hoon`,
`desk/tests/lib/urui-shell.hoon`, `tests/browser/real/settings.spec.js`,
`tests/browser/real/ace-undo-redo.spec.js`,
`graph-viz/desk/lib/gviz-web.hoon`,
`graph-viz/tests/browser/real/css-cascade.spec.js`.

New frame furniture, urui-owned end to end: a `#settings` button emitted
immediately before the consumer's toolbar marl, and a `#settings-modal`
dialog beside the help panel in both the full and compact frames.

- **The theme control moves into the modal**, at the same `#theme` id
  the runtime has always bound, so the js is untouched. Consumers must
  delete their own — two `#theme` elements in one page would be a
  duplicate id, and `++test-shell-page` now pins the page to exactly
  three `<option>`s to catch it.
- **Keybindings radios** (`#keys-ace`, `#keys-vim`) select the editor
  keymap; see W10.6.
- **The button is right-justified.** `.app-header` is `space-between`,
  so a third child would sit in the middle of it; `.settings-button`
  takes `margin-left: auto` to absorb that slack and land hard right,
  one header gap left of whatever the consumer's toolbar begins with.
  Stacked narrow, the auto margin is reset so it is a full-width row
  like the toolbar below it.
- **Screen format** is two pictogram buttons, `#layout-columns` and
  `#layout-rows`, drawn as css boxes rather than images so they take the
  frame's own border and accent colours in either theme. `setLayout`
  writes `data-layout` on `#workspace`; the stylesheet does the rest.
  `columns` is reference, editor and render side by side; `rows` is
  reference beside editor stacked over render. The reference pane is
  vertical and leftmost in both — only the workspace changes.
- **Each format keeps its own divider position**: `--editor-width` for
  columns, `--editor-height` for rows, persisted as `paneWidth` and the
  new `paneHeight` slot. The splitter reads `layout` to pick its drag
  axis and its arrow keys, and carries the matching
  `aria-orientation`.

Three new consumer slots: `preferences.layout`,
`preferences.keybindings`, `paneHeight`.

**Behaviour change, decided 2026-09-25:** the narrow query no longer
restacks the panes, hides the explorer resizer, or drops the splitter.
The screen format is the user's choice at every viewport width and every
divider stays draggable, so the 760px query now only relaxes minimums.
graph-viz's render-pane divider border moves from that query onto
`.workspace[data-layout='rows']`, where it belongs.

## 6. Assumptions this plan makes

1. **Hard cutover, no `$area` shim.** urui is pre-release with one live
   consumer, and syncing already requires a paired consumer commit.
2. **`permanent-views` moves into the reference pane.** `permanentViews`
   keeps emitting under the same json key, so no runtime reader changes.
3. **`emit:urui-config` takes a `$shell-spec`.** The runtime needs band
   data; only the spec has it. Consumers change one call site.
4. **Marl is never emitted to json.** A `%controls` band's json carries
   its name, reveal state, and the tag — the markup itself stays in the
   page, exactly as `controls=marl` does today.
5. **Three levels is a css limit, not a mold limit.** `levels` is a
   list; `urui-css` styles depths 0–2 and a fourth would inherit depth 2.
6. **A reveal flag is per-pane-per-band, not per-tab.** An open
   attribute sub-pane stays open when the user switches document tabs.
   A consumer that wants the flag to follow the selection calls
   `runtime.panes.reveal` itself on activate; nothing in the mold
   changes either way.
7. **heathcliff is not in scope.** It has no web front end yet; the mold
   is designed to fit a clay explorer plus a permissions pane, but
   nothing here implements it.
